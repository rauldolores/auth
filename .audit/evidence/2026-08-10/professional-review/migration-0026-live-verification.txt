TEST 5 — NEW edge case probed this run: does the UPDATE trigger cover organization_id changes,
not just status changes? ("what if the organization_id changes?" per this run's brief)
=====================================================================

Function prevent_last_owner_deactivation's short-circuit is:
  if old.status is distinct from 'active' or new.status = 'active' then return new; end if;
This only inspects status. It never inspects whether NEW.organization_id differs from
OLD.organization_id. Hypothesis: moving the sole Owner's membership row to a DIFFERENT
organization_id while leaving status='active' unchanged would never enter the owner-count
check at all, regardless of how many active Owners the *source* org has left.

Sub-test 5a — as postgres superuser (RLS bypassed, isolates the trigger's own logic):
  BEGIN;
  UPDATE kontrolia_auth.memberships SET organization_id = <CRM Demo id>
    WHERE id = 'd851c8dd-...' (Mi empresa's sole Owner, status stays 'active');
  SELECT count(*) active owners remaining in Mi empresa;
  ROLLBACK;
Result: UPDATE 1 (no exception raised). Remaining active owners in Mi empresa: 0.
==> Confirms the hypothesis: the trigger itself has no organization_id-change guard. This is a
real gap in the trigger's own logic, independent of RLS.

Sub-test 5b — does RLS's implicit WITH CHECK mitigate this for an ordinary single-org Admin?
  As authenticated role, sub=ab44dde8 (Admin of CRM Demo, only "member" of Facturación Demo):
  BEGIN; SET LOCAL role authenticated; SET LOCAL request.jwt.claim.sub = 'ab44dde8-...';
  UPDATE kontrolia_auth.memberships SET organization_id = <Facturación Demo id>
    WHERE id = '96b5df42-...' (CRM Demo's sole Owner, 302d8127);
  ROLLBACK;
Result: ERROR: new row violates row-level security policy for table "memberships".
==> Because the UPDATE policy has no explicit WITH CHECK, Postgres reuses the USING expression
as WITH CHECK, which is evaluated against the NEW row. So the caller must be is_org_admin() of
BOTH the source org (USING, old row) AND the target org (WITH CHECK, new row). A single-org
Admin (the precondition for PQ-SEC-003/PQ-SEC-004) CANNOT exploit this — confirmed blocked.

Sub-test 5c — is it exploitable by a caller who is an admin of BOTH orgs?
  Temporarily granted ab44dde8 an 'admin' role membership in "Mi empresa" (within the same
  rolled-back transaction), making them simultaneously Admin of CRM Demo and Admin of Mi empresa.
  BEGIN;
  INSERT membership + 'admin' role for ab44dde8 into Mi empresa;
  SET LOCAL role authenticated; SET LOCAL request.jwt.claim.sub = 'ab44dde8-...';
  UPDATE kontrolia_auth.memberships SET organization_id = <CRM Demo id>
    WHERE id = 'd851c8dd-...' (Mi empresa's sole Owner, 778686ba, status stays active);
  RESET role;
  SELECT count(*) active owners remaining in Mi empresa;
  ROLLBACK;
Result: UPDATE 1 (succeeded, no RLS rejection this time — target org check now passes too).
  Remaining active owners in Mi empresa: 0.
==> Confirmed live-exploitable, but ONLY by a caller who is simultaneously an Admin/Owner of
both the victim's current org and some other org they control — a materially narrower
precondition than PQ-SEC-003/PQ-SEC-004 (any single-org Admin). No application code path
performs this operation (organization-members PATCH only ever sets {status}, never
organization_id — grepped apps/auth-server/app/api/organization-members/route.ts to confirm);
reachable only via direct PostgREST/authenticated API access with a known membership UUID.
Tracked as new finding PQ-SEC-005 (HIGH, not CRITICAL, given the narrower precondition).

surface the raw Postgres error to the end user.
