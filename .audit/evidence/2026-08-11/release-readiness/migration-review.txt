MIGRATION SAFETY
- All 7 migrations are contiguous (0024-0030), no gaps.
- No destructive operations: no DROP COLUMN, DROP TABLE, TRUNCATE, bulk DELETE, or data-mutating
  UPDATE against existing rows anywhere in 0024-0030. Every statement is CREATE OR REPLACE FUNCTION,
  CREATE TRIGGER, or DROP TRIGGER IF EXISTS.
- Fully transactional: no CREATE INDEX CONCURRENTLY, no explicit COMMIT mid-file, no ALTER TABLE ADD
  COLUMN (so no NOT-NULL-without-default lock risk this round).
- Idempotency gap (non-blocking, style only): 0024:55, 0025:55, 0026:63,109, 0028:50,68, 0029:106
  create new triggers with bare `create trigger` instead of `drop trigger if exists` first, unlike
  the codebase's own established pattern (0019:190, 0024:35, 0030:389). Harmless under the actual
  filename-tracked runner (each file applies exactly once) — only bites a manual re-paste into the
  Supabase SQL editor.
- 0030 redefines is_org_admin/is_org_owner/custom_access_token_hook plus 4 trigger functions via
  CREATE OR REPLACE FUNCTION; verified parameter names match originals (0009/0011/0020/0021/0007/0016)
  exactly, so none hit Postgres's "cannot change name of input parameter" error.
- Cascade-delete paths correctly special-cased in 0025-0030 guards (`not exists (select 1 from
  organizations where id = ...)`), consistent with memberships/membership_roles FKs being
  ON DELETE CASCADE (0005_memberships.sql:18) — legitimate org deletion is not blocked.

MIGRATION ORDERING
- packages/db/src/migrate.ts:18-63 — filename-based tracking via kontrolia_migrations(filename text
  primary key), remaining .sql files applied in filename-sorted order, each inside its own
  BEGIN/COMMIT/ROLLBACK transaction, filename recorded only on success.
- Fresh install (0001-0030 in order) and incremental existing-install upgrade (already has 0001-0023,
  runs `migrate` and picks up exactly 0024-0030) both correctly supported by this design.
- 0028 documents its own same-day regression (service-role auth.uid() is NULL, breaking Owner-role
  grant on invitation accept) which 0029 fixes forward. Since migrate() always applies every pending
  file through the latest in one run, this window is unreachable through any real CLI path
  (install/update/migrate) — only reachable by manually cherry-picking migration files out of order,
  which the tool never does.

ROLLBACK SAFETY
- No down-migration mechanism exists (no *_down.sql, no `migrate down` command). Forward-fix-only —
  0029 is a same-day forward fix for a bug 0028 introduced, not a rollback.
- Each file's DDL runs in its own transaction, so a mid-file failure leaves the DB at "all files
  through N-1 applied, file N untouched" — never a half-applied migration. migrate() throws with the
  failing filename; CLI surfaces it and exits non-zero; re-running `migrate` safely resumes from the
  failed file.

CLI MIGRATE MECHANISM
- packages/cli/src/index.ts:31-45 (migrate), :112-152 (update), :246-266 (install auto-provision) all
  funnel into @kontrolia/db's migrate(), which opens a direct raw pg.Client TCP connection using
  whatever connection string the user pastes into a plain p.text prompt (index.ts:34-37) — not the
  Supabase Management API. No validation of the string beyond non-empty.
- FINDING: no confirmation, no dry-run, and no backup prompt anywhere in this path (grepped
  packages/cli/src for "backup"/"dry-run": zero matches). Goes straight from "connection string
  entered" to "spinner: applying migrations." Structural gap for a tool that runs against real user
  production databases — not specific to this release's (non-destructive) content, but a standing
  risk for any future destructive migration. Classified WARNING/FAIL for this release (migrations
  shipped today are non-destructive) — tracked as REL-DEPLOY-001 for future hardening.
- Minor: kontrolia_migrations bookkeeping table created without schema qualifier (migrate.ts:20),
  lands in default search_path schema (typically public), slightly at odds with the tool's own doc
  comment that migrations "only ever touch the kontrolia_auth schema."
